## The API

- **Alpha:** `https://jules.googleapis.com/v1alpha/…`. "Experimental … we may change specifications, API keys, and definitions." Pin the adapter to `v1alpha` and expect changes.
- **Auth:** an API key in the `X-Goog-Api-Key` header. It is made in the Jules web app (Settings → API), tied to the Google account; at most 3 keys; a key found public is disabled automatically. The Jules GitHub app must be installed on each repo first.
- **Repos:** `GET /v1alpha/sources` lists them as `sources/github/{owner}/{repo}` (with default branch and branches); `pageSize` up to 100.

| Call           | Method and path                           | Notes                                                                                                                                                                                                                                                       |
| -------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start a task   | `POST /v1alpha/sessions`                  | Body: `prompt`, `sourceContext: { source: "sources/github/o/r", githubRepoContext: { startingBranch } }`, `title`, `requirePlanApproval` (unset: plans auto-approved), `automationMode: "AUTO_CREATE_PR"` (default: no PR)                                  |
| Read status    | `GET /v1alpha/sessions/{id}`              | `state`, `url` (web view), `outputs[].pullRequest { url, title, description }`                                                                                                                                                                              |
| Activities     | `GET /v1alpha/sessions/{id}/activities`   | Paged (`pageSize` ≤ 100); one of `planGenerated`, `planApproved`, `progressUpdated`, `agentMessaged`, `userMessaged`, `sessionCompleted`, `sessionFailed { reason }`; artifacts `changeSet` (git patch), `bashOutput` (command, output, exit code), `media` |
| Approve a plan | `POST /v1alpha/sessions/{id}:approvePlan` | Only needed with `requirePlanApproval: true`                                                                                                                                                                                                                |
| Message        | `POST /v1alpha/sessions/{id}:sendMessage` | `{ prompt }`; the reply comes as a later activity                                                                                                                                                                                                           |
| Cancel         | none                                      | The API has no cancel, stop or delete. The web app can pause and delete a task.                                                                                                                                                                             |

Session states: `QUEUED`, `PLANNING`, `AWAITING_PLAN_APPROVAL`, `AWAITING_USER_FEEDBACK`, `IN_PROGRESS`, `PAUSED`, `FAILED`, `COMPLETED`.

## What the adapter (AI-240: M9.10) must handle

- **Start:** create with `AUTO_CREATE_PR`, `requirePlanApproval` unset (auto-approved), `startingBranch` = the run's base branch, `title` = `<KEY>: <ticket title>`. Store the session `id` and `url` on the run.
- **No cancel:** cancelling a Jules run marks it cancelled here only. The session may finish, use a daily task and open a PR anyway: AI-244 must leave a PR from a cancelled run alone (close it or flag it, never move the ticket). Say so on the ticket.
- **Plan approval and questions:** with plans auto-approved, `AWAITING_USER_FEEDBACK` is the state to watch. The watchdog should treat it as failed (or forward it as a ticket question later), never wait forever.
- **Errors:** retry only on 429 and 5xx, with the existing caps. Treat any 4xx as a refused start with the response body (clipped) as the reason, since the codes aren't documented.
- **Alpha:** keep field parsing tolerant (unknown fields ignored, missing `outputs` = no PR yet), behind one module.

## Matching a Jules PR to its run (AI-244: M9.11)

The branch name can't be relied on (undocumented), and the description marker is unverified. Recommended, in order:

1. **Session output:** the run stores its session `id`. When a `pull_request` opened webhook arrives for a registered repo, check the repo's in-flight Jules runs (capped by the provider's concurrency) with one `sessions.get` each, and match the PR's URL to `outputs[].pullRequest.url`. These are on-demand reads triggered by the webhook, not polling (ADR-0017, ADR-0018).
2. **Ticket key in the description:** the prompt asks Jules to start the PR description with `<KEY>: <title>`. If a live session shows it's honoured, the existing rule (key from the head branch or the description's first line, `pull-requests.ts`) moves the ticket with no new code.
3. **Deadline:** the run watchdog reads the session once at the deadline. `COMPLETED` with a PR URL finishes the run; anything else fails it, as ADR-0018 says.

## Follow-ups for other tickets

- **AI-232: M9.5 (google-sub quota):** the window is a rolling 24 hours, not the UTC day. Count Jules runs created since `now − 24h` with `countCreatedSince`, and use the plan's daily limit (15, 100 or 300).
- **Dispatch:** google-sub needs a concurrency cap equal to the plan's (3, 15 or 60), or sessions queue at Jules while counting against the day.
