# AI-364: The dispatcher and gate match what a coordinator session does — findings

**Status: done (2026-11-23).** Written from the code on `main` at `6047c055`. Andy, 2026-11-23: don't retire the coordinator. Match its behaviour in the control plane, and he will see which way makes sense later. Desktop sessions stay a supported way to build. Nothing is removed: `platform/procedures/coordinate.md`, `docs/runbooks/coordinating-sessions.md` and `scripts/coordinator/` stay.

Terms used here:

- **Coordinator:** a desktop session that hands tickets to worker sessions and merges their PRs (`coordinate.md`).
- **Dispatcher:** `BuildDispatcher` in `packages/domain/src/build-dispatch.ts`. It starts agent tasks on Ready tickets when a project has `autoBuild` on.
- **Gate:** `PullRequestGate` in `packages/domain/src/gate-service.ts`. It judges and merges agent PRs (branches `agent/<KEY>/…`).
- **`merge_pr`:** the MCP tool in `apps/api/src/merge.ts` (AI-220). A session asks it to merge one PR.
- **Merge queue:** AI-110: M5.18: Merge queue per repo, `packages/domain/src/merge-queue.ts`, ADR-0150. **It is on PR #403 and had not merged when this was written**, so every statement about it is marked _(PR #403)_.

## 1. Coordinator jobs against the control plane

Does: the control plane does the job today. Partly: it does part of it, for agent tasks only, or only once PR #403 merges. Not: it doesn't do the job.

An unknown or empty `touches` list overlaps everything. It can't see desktop sessions: their branches and open PRs aren't runs.                                                                                                                            |

## 3. Desktop sessions and the dispatcher on one project

What keeps them from merging over each other:

| Guard                         | Today                                                                                                                                                                                                           | Source                                 |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| The ticket stage is the claim | The dispatcher takes only Ready tickets. A session that moves its ticket to In progress takes it out of dispatch.                                                                                               | `build-dispatch.ts`                    |
| Different branches            | Agent PRs use `agent/<KEY>/…`. The gate acts only on those; session PRs go through `merge_pr`.                                                                                                                  | `gate-service.ts` `AGENT_BRANCH`       |
| One verdict for both          | The gate and `merge_pr` both use `mergeVerdict`: up to date with main, every check and both reviews pass, no accepted label, no kept path.                                                                      | `merge-verdict.ts`, `merge.ts`         |
| Pinned merge                  | Both merge only the judged head, after re-reading the base tip.                                                                                                                                                 | `merge.ts`, `gate-service.ts`          |
| One merge per repo at a time  | _(PR #403)_ Both go through the per-repo queue under a lease, across instances. Before it merges, `merge_pr` calls stay one at a time by rule, and the gate and `merge_pr` can each merge on the same base tip. | `merge-queue.ts` (PR #403), `merge.ts` |

What stays a rule people follow:

- **A coordinator must not leave tickets in Ready that it means to give to a worker.** Move each one to In progress before starting the worker, or the dispatcher may take it first. This only applies with `autoBuild` on.
- **File overlap between a session and an agent task isn't checked** (P1). The coordinator reads in-flight runs (MCP `list_in_flight`) before it briefs.
- **ADR numbers** (P2): before it reserves one, the coordinator checks the highest file and the numbers in-flight runs have reserved.
- **Main red** (P3): after each merge, check main's runs by hand.
- **Until PR #403 merges:** one `merge_pr` call at a time, and none while an agent PR is about to merge.

## 4. Turning `autoBuild` on for project AI (don't do it yet)

MCP `status` on 2026-11-23 showed `runsAtOnce: 2`, `paused: false` and `lastDispatch: null`: the dispatcher has never run for project AI.

Preconditions, from the code:

1. **Builds enabled** (`buildEnabled`), which Andy sets in the app only (`config-revert.ts`), then `autoBuild` on. The dispatcher returns at once without both (`build-dispatch.ts`).
2. **An executor and route:** project default `actions`; size S routes to the fast tier, Sonnet on the Claude subscription (MCP `status` routing). The repo needs the Actions build workflow and its OIDC trust in place.
3. **Room under the caps:** `runsAtOnce` 2, global 4, fewer than 5 agent PRs waiting, quota not at reserve (`dispatch-caps.ts`).
4. **Ready tickets that qualify:** in an approved milestone, Definition of Ready met, blockers Done, not assigned to Andy, with honest `touches`. An empty list overlaps everything, so one run at a time.
5. **Merge mode saved:** `all-clean` for project AI (runbook §5). With no mode, nothing merges (ADR-0134).
6. **The procedural guards in §3** agreed with any coordinator running at the same time: move tickets to In progress first, and read `list_in_flight` before briefing.
7. **Preferably after PR #403 merges**, so the gate and `merge_pr` can't both merge on one base tip.

After the first dispatched ticket, check:

- `status` shows `lastDispatch` with a start, not an idle reason. The run appears in `list_in_flight` with the expected route.
- The PR's branch is `agent/<KEY>/…` and its description starts with the ticket link. CI and both review checks run on it, and the review agents give it a real review (ADR-0141), not "not reviewed".
- The gate's verdict is recorded on the run (`gateReasons`, mode). With `all-clean` it merges, or _(PR #403)_ queues. Main's own checks pass on the merge commit (checked by hand, P3).
- The ticket moves to Ready for review, then Done. Cost and quota show in the digest. No coordinator worker touched the same files.
