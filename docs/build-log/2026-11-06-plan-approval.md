# 2026-11-06 — Plan approval: a read-only plan run Andy approves before the build (AI-33: M1.8a)

- **What:** a project's `planApproval` policy (ADR-0050: `none` default, `m-and-l`, `all`) is now acted on. When it covers the ticket's size, any build start (dispatcher, REST, UI, MCP `build`) starts a read-only `plan` run instead (`platform/procedures/plan.md`, `plan.schema.json`: summary + the build plan). Its report stores the plan on the Run, flags the ticket and starts nothing; the ticket stays Ready.
- **Decide:** `POST /api/projects/{p}/tickets/{t}/runs/{run}/plan-decision`, the Runs panel (**Approve plan**, a reason field, **Reject plan**) or MCP `approve_plan` / `reject_plan`. Owner-only: `RunService.decidePlan` refuses any actor but `andy` (403); the decision records the signed-in email and time on the plan Run (`planDecision`). Approve starts the build with the plan in an `<approved-plan>` block (escaped, marked as agent text); `build.md` returns it unchanged and records departures as deviations; the build Run records `planRunId`. If the build can't start yet (another run in flight), the approval stands and a comment says so. Reject needs a reason, keeps the flag and starts nothing; Andy's next start re-plans, and the plan prompt lists up to 3 rejected plans with their reasons.
- **Dispatcher:** skips a ticket whose latest plan is running, awaiting a decision or rejected (even after Andy clears the flag); a ticket that needs a plan gets a plan run; an approved plan's build starts on the next event.
- **Caps and staleness (ADR-0028):** ≤ 3 plan runs per ticket (the dispatcher flags at the cap); plan run 50 turns, deadline 45 minutes, same model as the build. A plan is stale, so it is re-planned rather than approved, when it is over 72 hours old, the project's policy changed (`Run.planPolicy`), or the ticket changed. "Changed" means the ticket snapshot the build would see (title, body, criteria, assumptions, size, scope, answers) is no longer in the plan run's prompt, not `updatedAt`: flag toggles and board reordering bump `updatedAt` and would have made every plan stale. An automatic build retry never turns into a plan run.
- **Refine questions on AI-33 (answered by Andy, 2026-11-06):** a rejected plan waits for Andy's explicit start; owner = actor `andy` (signed-in user or his MCP token); a plan whose ticket or policy changed, or over 72 h old, re-plans; explicit starts always plan first when the policy applies. Refine's added criteria hold too: no plan run under `none` or for S under `m-and-l`; a second decision is refused (409); a failed or invalid plan run flags the ticket (after one retry for a reported failure) and starts no build.
- **Review answers (fffd42b):** a plan decision is written once: `applyRunPatch` (both run stores, inside their transaction) refuses a second `planDecision`, so a racing approve and reject can't both win (contract test on the fake and Firestore). Approving no longer clears Needs-you itself: the build's start does, so a build that can't start yet stays in the inbox. The agent-written plan in the build prompt (security info) stays as designed: Andy reads the full plan in the run's report before approving.
- **No new ADR:** ADR-0063 already named a separate read-only plan run as this PR; caps and staleness fill in ADR-0050's details.
- **Tests:** `build-flow.test.ts` drives policy `all` in-process: plan run → flagged, Ready → dispatcher skips it unflagged and plans the next ticket → reject without a reason (409), with one → re-plan sees it → approve → build with `<approved-plan>` → PR. Domain: `plans.test.ts` (policy, state, prompt), `plan-approval.test.ts` (m-and-l, owner-only, stale, decided twice, not latest, caps, dispatcher). Schema sync in `build.test.ts`; MCP tools; the Runs panel's reject path.
