andy-intelligence · design and UX review · 2026-11-23

The UI is tidy. It is not yet designed.

The 2026-11-21 review removed clutter and fixed the phone. What is left is an unstyled shadcn default: grey boxes, the system font, native form controls, and no feedback when something changes. Three directions are mocked below for the Needs-you inbox and Project settings. Pick one and the rest follows from it.

Verified: 27 screens rendered at 1280×800 and 390×844, light and dark, against the seeded fake API (198 images, system Chrome, throwaway spec removed). Production untouched. Not verified: live interactions after a click (answering, saving, drag), GitHub and Local runners beyond their error state, and real data volumes.

1 · Critique

What the screens show today

Visual

  • Type has no hierarchy. System font, four sizes, the largest 18 px medium. A page title and a section heading look alike.
  • Colour is the library default. Every neutral has zero chroma and the one action colour is black. Status tints are the only colour, and they work.
  • One kind of surface. Everything is a white box with a 1 px grey border. Nothing is raised, sunken or selected, so nothing leads the eye.
  • Width is unmanaged. Lists stretch to the full window; forms stop at 672 px. Neither uses the screen.
  • Nothing moves and nothing confirms. An answered card disappears; a saved setting shows grey "Saved" text. No toast, no transition, no skeleton while loading.
  • Empty states are a sentence. Roadmap, dashboards and the agent task page leave most of the screen blank.

Interaction

  • Every picker is a native select that shows raw enum values and hides the other options' meaning. Merge mode, plan approval, default worker, executor, environments, tiers and routes.
  • Switches are native checkboxes, about 13 px, with the consequence written in small grey text below.
  • Keyboard exists but is invisible. Shortcuts shipped (AI-338: Keyboard: move through and act on the inbox and board without the mouse), yet no key hint appears on any control and there is no command palette, though M3: New UI and MCP lists one.
  • Six primitives in components/ui/: badge, button, chart, dropdown menu, input, segmented. No select, switch, dialog, tooltip, toast, tabs or field wrapper, so every page hand-rolls them.

Flow: new idea to merged work

  • Add project is three fields and then drops you on an empty board.
  • The brief has no form; it exists only over MCP.
  • "Start plan-project task" sits inside Project settings, and the plan to approve appears there too.
  • The empty roadmap says to "ask a Claude session". Ideate is a button on the board.
  • So one path crosses Settings, Roadmap, Board and Inbox with no guide. It needs one visible sequence: Brief → Plan → Approve milestones → Build, shown on the project until it is done.

Where design.md holds the UI back

Rule today Change to
"Nothing animates." Motion explains a change: 120 to 180 ms, opacity and transform only, off under reduced motion, never delays input.
System font, four sizes, nothing above text-lg. One chosen face plus a mono for keys and numbers; a six-step scale with a real page title.
Eight colour roles, all neutrals grey. Add surface levels (sunken, base, raised), a selected state, and an accent that is not black. Tinted neutrals.
"Content is full width"; forms cap at max-w-2xl. Three page templates: list with detail, settings with section nav, reading page.
Component list: Button, Badge, DropdownMenu. Name the full set and forbid native select and checkbox. A picker with fewer than six options shows all of them with descriptions.
Dark mode from the OS only. A switch (system, light, dark); dark screenshots in the check.
No rule for feedback. Every write confirms where it happened, and a toast offers Undo when the write can be reversed.

Keep: density, sentence case, role colours as tints, "status visible without opening anything", the copy rules.

The bar: three reference products

  • Linear, for the whole: a dense tracker one person drives from the keyboard, with list and detail side by side and motion that never slows it.
  • Vercel dashboard, for settings: every option on screen with a plain description, one card per setting, saved in place.
  • Superhuman, for the inbox: triage as a flow, one decision in focus, a key on every action, and Undo after each.

3 · Screenshots on UI PRs

AI-353: UI PRs show before and after screenshots

The stored images are committed, and the repo is public, so both versions of every changed image already have a URL: the base commit's and the PR head's. Nothing needs uploading.

  • Recommended: a script (pnpm screenshots:table) writes a "Before and after" table into the PR description, one row per changed image. The existing release-note check fails a PR that changes a stored image without that table. The check also prints the table to the job summary. No new permission.
  • Alternative: a bot comment with the same table. Needs pull-requests: write on a new job, which is a permission change you merge, and it buys little over the description.
  • Gap to close first: only 30 images exist, all light, and several screens have none (Models, Add project, GitHub, Local runners, dashboards on a phone). A screen with no stored image shows no before. Add one desktop and one phone image per screen, plus dark for the shell, inbox, board and settings, inside the five-minute cap.

The design milestone should require it, and it should be the first ticket: every ticket after it is a visual change you will want to judge from the PR. The workflow edit is yours to merge.

Three things to decide

Which direction: A, B or C?It sets the shell, the tokens and every later mockup. Recommended: A, with B's card on the phone.
Design system first, or screens first?System first costs four tickets before a screen looks different, but each screen is then built once. Screens first shows change sooner and reworks each screen when the components land. Recommended: system first.
Is this M11, ahead of M4, M5 and M10?Those three are approved and the build is paused for the review. Running M11 first restyles screens that M4 and M5 will still add to; running it after means new screens are built in the old style. Recommended: tickets 1 to 5 now, screens after the product review settles which screens stay.
