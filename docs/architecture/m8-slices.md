# M8: Project members — slices

Slice table for [milestones.md §M8](milestones.md#m8-project-members). Epic: AI-18: M8: Project members. Each ticket holds its acceptance criteria, out of scope, full `touches` (files it owns) and merge note. **Risk** says how closely to review (high = sign-in, allow-list or permissions); it does not decide who merges. The coordinator merges every clean PR except Andy's four kinds (ADR-0120): here only AI-242: M8.1 (the design ADR) and AI-272: M8.14 (needs his hands).

**Already built, not sliced:** one permission function (AI-19: `domain/src/permissions.ts`, `can`/`requireCan`); history actors are `user:<uid>`, never an email; push subscriptions keyed by uid with `deleteAllForUid` (M7); the config change log (AI-118).

**Design in one paragraph** (recorded by M8.1 as ADR-0127, proposed): guests, not tenants. The owner is whoever is in `ALLOWED_EMAILS` (Andy). A project's members are a per-project email allow-list (Andy, 2026-11-10) with role `contributor` (create, edit, comment, move forward, answer) or `viewer` (read). Memberships live in Firestore; a signed-in user gets in if they are an owner or hold a membership, and access is re-resolved per request, so removal is immediate. `can(principal, action, projectId)` decides every write from one role table; a project a caller can't read answers 404. Contributor text stays untrusted agent input, so queuing to Up next (which starts refine on Andy's quota) stays owner-only. No member can exist until every gate has shipped: M8.9 (adding members) waits on M8.5 to M8.8. No slice needs IAM, Terraform or a secret: any Google account already reaches the app-level gate (ADR-0010).
