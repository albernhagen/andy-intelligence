# 0102 — Local build and publish: the platform's own publish script, one push token, a fail-closed Bash check

AI-133: Local executor: local build and publish (ADR-0089 slice 6). The runner now runs build tasks. Sync tasks stay on GitHub Actions (ADR-0094: the claim never hands one out).

## Residual risk (R-AI-44)

- "Once per run" is read-then-write, as on Actions (`claimPushGrant`): two requests in the same instant could both get a token. Only the runner that claimed the run holds its per-run token, and it already has the run's push authority.
- A 1-hour App token for one repo is on the Mac during publish (ADR-0089 open question 4). It can push agent branches and open PRs, never `main` (ruleset).
- A process an injected agent leaves behind (`setsid`) can outlive it while publish runs. It stays in the agent's Seatbelt profile, which can't read the work directory where git's credential file lives, and it can't read the publish child's memory. It can read other same-user processes' arguments and environments (Seatbelt can't deny that), which hold no token.
- Whether Claude Code's sandbox starts inside Seatbelt is unproven: if it doesn't, every local build fails at the Bash check until Andy decides (open question).

## Open question for Andy

If the Bash check fails on the Mac because Claude Code's sandbox can't start inside the runner's Seatbelt, should local builds run Bash under the runner's Seatbelt alone?

The live check below tells whether nesting works. If it doesn't, local builds can't run at all today.

- Keep failing closed (this ADR): no local builds until nesting works; Actions builds them. Costs nothing new.
- Seatbelt alone, Claude Code's sandbox off: Bash writes only the checkout and reads no home or Keychain, but its network is open HTTPS (ADR-0101 allows port 443), so an injected agent can send the checkout anywhere. A new ADR and a high-risk PR.
- Recommendation: keep failing closed, and revisit only if Actions minutes become the limit.

Live check: as `ai-runner`, set one small ticket's executor to `local` and let the runner claim its build. The report either says "Bash sandbox check passed" in the runner's log and opens a PR, or fails with "the check command didn't run in Bash".

## Consequences

- Good: a `local` build opens the same `agent/<KEY>/<runId>` PR as Actions, through the same checks, and asks for its push token once.
- Bad: whether local builds can run at all is known only after a live run; the check costs one Haiku call per build.
