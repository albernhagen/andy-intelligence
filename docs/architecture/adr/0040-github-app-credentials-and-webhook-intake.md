# 0040 — GitHub App credentials and webhook intake

Decided by Andy, 2026-11-02 (M1.5: GitHub App + project registration). Also answers ARCHITECTURE open question 8.

## Context and Problem Statement

M1.5 needs: a GitHub App the control plane acts as (`CodeHost` port), a webhook receiver for PR, check and workflow events, a registered first project, and an App token for the PRs the system security review opens (PRs opened with `GITHUB_TOKEN` don't run their checks until Andy approves them). The App's private key and webhook secret are credentials; the repo is public (ADR-0015).

## Decision Outcome

| Question                        | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First project (open question 8) | `albernhagen/andy-intelligence` is project #1 (key `AI`), so the system dogfoods itself; side projects follow in M2: Multi-project in parallel.                                                                                                                                                                                                                                                                                                     |
| Apps                            | **Two Apps**, both private to Andy's account, created with GitHub's manifest flow (`platform/github-app/*.json`). **Control-plane App** (`andy-intelligence`): read-only (metadata, contents, pull requests, checks, actions); events `pull_request`, `check_run`, `workflow_run`. M1.6: Claude Code executor adds `actions: write` for dispatch. **Review bot App**: contents + pull requests write, no webhook, installed on this repo only.      |
| Why two Apps                    | The review bot's key has to live in GitHub (Actions). If it were the control-plane App's key, a leak could mint tokens on every repo the control-plane App is later installed on (all managed projects). A separate bot limits that to this repo, which the job could write to anyway.                                                                                                                                                              |
| Control-plane App credentials   | Private key and webhook secret in **Secret Manager** (`github-app-private-key`, `github-webhook-secret`). Terraform creates the empty secrets; Andy adds versions with `gcloud` piped from the manifest conversion, so values never touch tfvars, state, chat or disk. The runtime SA gets `secretAccessor` on those two secrets only; Cloud Run reads `latest` as env vars. App ID (not secret) is the tfvar `github_app_id`; unset = feature off. |
| Review bot credentials          | Private key in the `system-review` GitHub environment (deployment branches: `main` only), so workflows on other branches can't read it (narrows risk R2 for this secret). Client ID as a repo variable. The token is minted after the agent step, scoped to contents + pull requests write.                                                                                                                                                         |
| Webhook receiver                | `POST /webhooks/github`, public. Checks in order: body ≤ 1 MB → ≤ 300 requests/minute per instance (max 2) → HMAC-SHA256 of the raw body (`X-Hub-Signature-256`, constant-time) → event type → repo registered to a project → record. `ping` → 200; other events and unregistered repos → 202, not stored.                                                                                                                                          |
| Idempotency                     | One Firestore document per delivery in `codeHostEvents`, keyed by `X-GitHub-Delivery` (GitHub keeps it on redelivery). Created with `create()`, which fails if the document exists: a replay returns `duplicate` and changes nothing. Port `CodeEventLog`.                                                                                                                                                                                          |
| What is stored                  | A normalized `CodeHostEvent` (kind, action, repo, project, PR number/state/refs/title ≤ 256 chars, check or workflow status/conclusion, URLs). Never the raw payload. Firestore TTL deletes records 30 days after receipt (ADR-0028).                                                                                                                                                                                                               |
| Registration                    | `POST /api/projects` with `repos`: each repo must exist with the control-plane App installed (`CodeHost.getRepo`), is stored with GitHub's spelling, and may belong to only one project. The receiver maps repo → project with a 60 s cache of the project list.                                                                                                                                                                                    |
| Libraries                       | `@octokit/auth-app` + `@octokit/core` (App JWT, installation tokens), `@octokit/webhooks-methods` (HMAC). New package `@andy/github`.                                                                                                                                                                                                                                                                                                               |

### Consequences

- Good: the control-plane key never leaves Secret Manager; replays are no-ops by construction; unregistered repos can't fill the database; review PRs run their checks unattended.
- Bad: two Apps to create and rotate by hand (runbook `github-app.md`). A flood of unsigned requests can use up the rate cap and make GitHub's deliveries fail until it stops (redeliver from the App's settings). Key rotation needs a redeploy (Cloud Run reads `latest` at revision start). The `CodeHost` contract suite against real GitHub runs only on Andy's machine.
