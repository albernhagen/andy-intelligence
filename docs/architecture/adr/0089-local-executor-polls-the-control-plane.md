# 0089 — Local executor: a runner on Andy's Mac polls the control plane for work

AI-44: Local executor, slice 1. Answers the local-executor part of ARCHITECTURE open question 11 (ADR-0032: Deployment modes). Andy's decisions on the ticket (2026-11-10) are inputs, not options: design first; the laptop only makes outbound calls ("Personal laptop should never have an open connection like that, this needs to be powered through the deployed system and/or polled from my local claude code"); a long-lived runner secret in the macOS Keychain, exchanged for short-lived per-run tokens; a run lost mid-way fails and Andy decides, no silent re-run; a project default plus a typed ticket override, never a label.

## Context and Problem Statement

Agent runs (refine, plan, build, sync) run only in GitHub Actions (ADR-0051, ADR-0063): about two minutes of runner setup per run, and no way to build on a private machine. Andy also builds tickets on his Mac by hand, outside the dispatcher, so the caps don't see that work. A local executor must:

- get work without anything listening on the laptop and without the cloud connecting in;
- never let two pollers, or a poller and Actions, take the same ticket;
- keep every guard Actions has: caps, the permission profile, the sandbox, publish checks, one push token per run;
- give the agent process no credential, as the Actions `agent` job holds none.

Terms. **Runner**: a small program on Andy's Mac (not an LLM) that polls, starts the agent, reports and publishes. **Agent**: the `claude -p` process the runner starts for one run. **Present**: the runner polled in the last 2 minutes.

## Considered Options

| Option                                                                                                   | Consequences                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Push: the runner holds a WebSocket or SSE connection and receives dispatches                          | Ruled out by Andy: an open connection on the laptop.                                                                                                                                                           |
| B. The control plane assigns a run to the runner (a `queued` local run) and the runner polls for it      | A run exists before anyone takes it: it holds a dial slot while the laptop may be asleep, needs an unclaimed-expiry path and a fall-back re-dispatch.                                                          |
| **C. Pull: the runner's poll asks the dispatcher for its next run; the run is created inside the claim** | No run exists until a present runner takes it, so nothing waits on a sleeping laptop. The claim reuses the dispatcher's selection and `RunService.start`, whose re-checks already stop a ticket running twice. |
| D. Andy's interactive Claude Code session polls over MCP and does the work in that session               | No new program, but the session holds Andy's MCP token (every tool, as Andy) while it reads untrusted ticket text; no profile or sandbox it can't change; one ticket at a time, blocking the session.          |

## Decision Outcome

Option C. Option D is open question 1.

### Getting work: poll, claim, lease

| Topic            | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Surface          | Plain HTTPS on `PUBLIC_URL`, not MCP (the runner isn't an LLM): `POST /runner/claim` (runner secret); then, with the per-run token, the run's existing `context`, `report` and `POST /github/token` calls plus a new `POST /runs/{id}/heartbeat`. Request and response schemas in `packages/contracts`.                                                                                                                                                                                                                                                                                                                                  |
| Polling          | Every 30 s while the runner has a free slot; none while full. The server answers `429` to a second claim from one runner within 10 s. Each claim records `lastSeenAt` on the runner: present = seen in the last 2 minutes.                                                                                                                                                                                                                                                                                                                                                                                                               |
| Claim            | The request names no ticket. The server runs the same selection the dispatchers use (`dispatchNext`: syncs, then builds, then refines), limited to tickets whose executor resolves to `local` in the projects the runner may serve, and starts the run through `RunService.start` (route `local`). The response is `{ run: null }` or the run ID, its per-run token and its deadline.                                                                                                                                                                                                                                                    |
| No double take   | `RunService.start` allows one run per ticket and re-checks the dial, the global cap and overlap after creating the run (ADR-0079, ADR-0080); the oldest run wins, a loser fails like a lost slot race. Two runners, or a runner and the Actions dispatcher, racing for one ticket: one run starts. While a runner is present, the Actions dispatcher skips tickets that resolve to `local`.                                                                                                                                                                                                                                              |
| Lease            | A claimed run has a 5-minute lease; the runner heartbeats every 60 s, which renews it. One Cloud Task per run (`WatchdogQueue`, named after the run) fires at lease expiry: renewed, it re-queues itself for the new expiry; not renewed, the run ends. The ADR-0055 deadline check still runs.                                                                                                                                                                                                                                                                                                                                          |
| Laptop sleeps    | Heartbeats stop, the lease lapses: the run is `failed` with reason `lease_lost`, **not retried** (amends ADR-0055 for local runs), the ticket is flagged Needs-you: "Local run lost: the runner went away", with retry-local, retry-on-Actions and take-over as Andy's choices. When the laptop wakes, its heartbeat and report are refused (run already ended; status changes are conditional), the push grant is refused (run not `running`), so it never publishes; the runner keeps the worktree for inspection and logs it. While a run is active the runner holds `caffeinate -i` (idle sleep only; closing the lid still sleeps). |
| Cancel           | Andy cancels as today; the next heartbeat answers `cancel: true`, the runner stops the agent and reports `cancelled`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Runner goes away | Each claim (re)queues one Cloud Task `runner-away` at `lastSeenAt` + 2 minutes, named per runner and minute. When it fires and the runner is still away, it wakes the dispatchers, which now send `local`-default tickets to Actions.                                                                                                                                                                                                                                                                                                                                                                                                    |

### Identity and credentials

| Credential          | What it is                                                                                                                                                                                                                        | May do                                                                                                                                                                            |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runner secret       | Minted in the UI (`/settings/runners`, Firebase sign-in + allow-list) and shown once; Andy pastes it into `local-runner login`, which stores it in the macOS Keychain. Stored as a SHA-256 hash; 90-day expiry; revoke in the UI. | `POST /runner/claim` only, for the projects ticked on the runner. No ticket, settings, MCP or read API. MCP can't mint, list or revoke runners: a stolen MCP token can't add one. |
| Per-run token       | Opaque, hashed, returned by the claim, bound to one run and runner; dies when the run ends or at its deadline.                                                                                                                    | What a verified Actions OIDC caller may do (ADR-0019): its own run's context, heartbeat, report (comment, questions, result) and one push grant.                                  |
| Push token          | The same 1-hour App token as Actions, from `POST /github/token` with the per-run token; `claimPushGrant` accepts a local run whose recorded runner and token match, once (amends ADR-0063).                                       | Contents and pull requests write on the run's repo, for the publish step. Never seen by the agent.                                                                                |
| Claude subscription | The runner user's own `claude` login (`claude setup-token`), in that user's Keychain.                                                                                                                                             | Model calls. Scrubbed from the agent's sandboxed Bash, as on Actions.                                                                                                             |

No secret is ever in the repo. Existing sign-in is reused where a person acts (minting and revoking in the UI); the runner, a program, gets its own narrow credential rather than Andy's MCP OAuth grant, which is good for every tool.

### What runs locally

- **Same steps, same rules.** Refine, plan, build and sync, each with its procedure, prompt and schema from `platform/` at the platform SHA the context names, never the project checkout. Turns, deadlines and change limits as on Actions.
- **Profile.** The executor profile (`platform/executor/profile.json`) passed with `--settings` and user, project and local settings sources off. Managed settings are machine-wide on macOS and would bind Andy's own sessions, so they aren't used. Slice 5 must prove project settings and hooks don't load; until then it is intent.
- **Isolation.** The runner and its agents run as a dedicated macOS user (`ai-runner`) that can't read Andy's home, Keychain, `gh` or SSH credentials (open question 2). Inside it, Bash only in Claude Code's macOS sandbox (Seatbelt), checked live before the agent starts (ADR-0071), network to the package registry only. Dependencies installed before the agent, scripts off (ADR-0072).
- **Results.** The runner parses the agent's stream (usage, `rate_limit_event`) and posts the same report as the `report` job: summary, tokens, cost estimate, quota reading (checked when written, R24), verification output; the sync step's executor checks run in the sandbox as on Actions (ADR-0083).
- **Publish.** The runner runs `scripts/executor-publish.mjs` from a platform checkout outside the agent's writable area, with the push token: same path rules, protected paths, size limits, `agent/<KEY>/<runId>` branch, PR as the App bot (open question 4).

### Fit with the dispatcher

| Rule                                              | Local runs                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Choosing local or cloud                           | Project `executor`: `actions` (default) or `local`. Ticket `overrides.executor`: `actions`, `local`, or empty (follows the project), a typed field like `overrides.assignee`, shown and edited in the story panel and over MCP (`set_executor`, `set_default_executor`). `resolveExecutor(ticket, project, runnerPresent)` is pure and read-time (like `resolveWorker`, ADR-0082): never copied onto the ticket. |
| Runner away                                       | Project default `local`: the run goes to Actions. Ticket override `local`: waits, status line "Waiting: local runner away" (open question 3).                                                                                                                                                                                                                                                                    |
| Dial, global cap, PR cap, pause, quota (ADR-0079) | Checked in the claim through `mayDispatch`, and again in `RunService.start`. Local runs count like any run.                                                                                                                                                                                                                                                                                                      |
| Overlap (ADR-0080)                                | Same selection, so a ticket overlapping a build in flight (on either executor) is skipped. `Run.touches` and reserved ADR numbers as today.                                                                                                                                                                                                                                                                      |
| Worker (ADR-0082)                                 | Only a resolved `agent` worker builds, on either executor. A ticket Andy works himself (`me`) never reaches the runner.                                                                                                                                                                                                                                                                                          |
| Sync runs (ADR-0083)                              | Routed by `resolveExecutor` like the ticket's build; global cap counts, dial doesn't, 3 a day per PR, as today.                                                                                                                                                                                                                                                                                                  |

### Caps (ADR-0028)

| Cap                          | Value                                                                        |
| ---------------------------- | ---------------------------------------------------------------------------- |
| Registered runners           | 2 (`MAX_RUNNERS`)                                                            |
| Runs at once on one runner   | default 1, max 2 (`LOCAL_RUNS_AT_ONCE`); still under the dial and global cap |
| Claims per runner            | 1 per 10 s (server-enforced, `429`)                                          |
| Failed runner-secret lookups | per-IP limit as on `/oauth/token` (R14)                                      |
| Cloud Tasks                  | one lease task per local run; one `runner-away` task per runner per minute   |
| Push tokens                  | one per run, as on Actions                                                   |
| Runner idle                  | exits after 12 hours without a claimed run                                   |

### Security

New entry points: `POST /runner/claim`, `POST /runs/{id}/heartbeat`, and the per-run token as a second identity on `context`, `report` and `/github/token`. New trust boundary: the laptop is now an executor host. Risk row `R-AI-44` in the threat model (open, mitigations planned); entry points listed in `agents-and-executors.md`.

| Attacker has                   | Gains                                                                                                                                                                                              | Bounded by                                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| A forged or replayed poll      | Nothing without the secret: `401`, rate-limited.                                                                                                                                                   | Hash lookup, per-IP limit.                                                                                                       |
| A stolen runner secret         | Claims runs on the ticked projects: ticket snapshots (public repo today), Andy's quota spent within the caps, a push token per run (agent branches and PRs, never `main`: ruleset), false reports. | Caps, quota reserve, revoke in the UI, 90-day expiry, ruleset on `main`, review agents and Andy's merge; R24 checks on readings. |
| A compromised laptop           | All of the above, and the runner user's Claude token. Andy's own `gh`, SSH and MCP credentials on the same Mac already give more.                                                                  | Separate user; revoke the runner and rotate the Claude token.                                                                    |
| An injected ticket (the agent) | What it has on Actions: the sandboxed checkout and registry network.                                                                                                                               | Profile, sandbox, scrub, publish checks; the agent never holds the runner secret, per-run token or push token.                   |

### Consequences

- Good: no inbound port and no held connection; nothing waits on a sleeping laptop; one claim path through the existing caps and races; the agent holds no credential, as on Actions.
- Good: a lost run is never re-run silently, so no duplicate branch or PR.
- Bad: two executor hosts with different sandboxes (bubblewrap on Actions, Seatbelt on macOS); the macOS sandbox and the `--settings` profile are proven only by slice 5's live check.
- Bad: a 30-second poll means up to 30 s before a local run starts, and about 2,900 small requests a day while the runner is up (Cloud Run and Firestore free tier).
- Bad: a dedicated macOS user is a one-time setup step and a second Claude login.
- Accepted: a runner that loses a run after its push but before its report leaves a PR the control plane doesn't know; the PR webhook (AI-14) still links it to the ticket.

## Open questions for Andy

1. **Should the local work run in a small runner program that starts a headless `claude` per ticket, or inside your own interactive Claude Code session?**
   You said work should be "polled from my local claude code". Both poll the control plane; the difference is who holds the credentials while the agent reads ticket text, which is untrusted.
   - Runner program (`local-runner start`, started from a terminal or a Claude Code session): holds a narrow runner credential; the agent gets none and runs under the fixed profile and sandbox; runs in the background without tying up a session. One more small app to build (slice 5).
   - Your interactive session, through MCP tools and `/loop`: nothing new to install, but the session holds your MCP token (every tool, as you) and your `gh` login while it reads ticket text, and its permissions are whatever that session allows; one ticket at a time.
   - Recommendation: runner program, so the local path keeps the same guards as Actions.

2. **How strongly should a local agent be kept away from the rest of your Mac?**
   A build agent runs project code and Bash. On Actions it runs on a throwaway machine; locally it would run next to your files and logins.
   - A dedicated macOS user (`ai-runner`): can't read your home, Keychain, `gh` or SSH keys; Claude Code's sandbox inside it. One-time setup (a user, a second `claude` login) in the runbook.
   - Your own user with Claude Code's sandbox and read denies for credential paths: no setup, but one sandbox gap reaches your logins.
   - A Linux VM or container running the same sandbox as Actions: closest to cloud, but needs Docker or a VM and gives back part of the start-up time saved.
   - Recommendation: dedicated macOS user.

3. **When a ticket is set to `local` and your Mac is away, should it wait for the laptop or go to GitHub Actions?**
   A project default of `local` falls back to Actions when the runner is away (the ticket's acceptance criteria). A ticket override is your explicit pick for that one ticket.
   - Wait: the ticket shows "Waiting: local runner away" until the runner polls again; useful for work that must stay on your machine.
   - Fall back: it runs on Actions like a project default; the override only matters while the laptop is up.
   - Recommendation: wait, so an explicit override always means what it says.

4. **Should the runner push the branch and open the PR itself, or send the change to the control plane to push?**
   On Actions a publish job with a 1-hour App token, bound to the run, checks the change and pushes.
   - Runner publishes: the same publish script and token rules as Actions, little new code; a 1-hour App token for one repo is on the laptop during publish.
   - Control plane publishes: no GitHub write token ever on the laptop, but a new server-side publish (patch upload, checks, commits through the GitHub API), about one more M slice.
   - Recommendation: runner publishes; the laptop already holds your own, wider `gh` login.
