# 0053 — Project brief: a living context source, written at onboarding through MCP or the UI

Decided by Andy, 2026-11-04. Answers open question 12 for the markdown kind of context source (ADR-0033); MCP and skill sources stay later.

## Context and Problem Statement

When Andy onboards a project he needs to give agents the idea, who it is for and the business, the vision, the goals and non-goals, and broad architectural expectations. That knowledge changes as features ship and direction changes. ADR-0033 named markdown docs in the repo as the first context source but left the file's shape, how it is written, how it evolves and which steps read it to a later design. Without that, the brief is a file Andy has to remember to write and keep current.

## Decision Outcome

| Topic             | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The brief         | `docs/product/brief.md` in the project repo, fixed sections: Idea · Users and business · Vision · Goals and non-goals · Architectural expectations (stack, cloud, environments, constraints, quality bar) · Open questions. Within a context budget (`context-budget.json`, carried by the baseline); longer material in sibling `docs/product/*.md` files the brief links to. Git is its history; no Firestore copy.                                                                        |
| Global layer      | Andy's standards stay in `template/AGENTS.md.template` (every project inherits them). The brief is the project layer; the step layer is the mapping below.                                                                                                                                                                                                                                                                                                                                   |
| One interview     | One procedure, `platform/procedures/onboard.md`: the question list per section, the suggested defaults, and the rendering of answers into `brief.md` (a template, no LLM needed). Two front ends, both supported: **`/onboard` skill** in the devkit (Claude Code or Claude desktop through MCP) that runs the interview conversationally and submits the answers with an MCP tool; **the UI's "new project" flow**, which asks the same questions as a guided form. Both call the same API. |
| What the API does | `POST /api/projects/{id}/brief` (and the MCP tool) takes the structured answers, renders `brief.md`, and opens a PR on the project repo with the App token (new project: together with the baseline files). Andy merges. Revising = the same call with the current brief as the starting point; the PR shows the diff.                                                                                                                                                                       |
| Who reads what    | Carried in each run request as `context` (§7.2): `ideate` and `refine` get the whole brief; `plan` and `build` get Architectural expectations plus `AGENTS.md`; the adversarial acceptance-criteria pass gets Goals and non-goals; the system security review gets Architectural expectations. Read through the `CodeHost` port at dispatch, never from an agent's own fetch.                                                                                                                |
| Keeping it true   | `refine` and `plan` check the ticket against the brief and raise a **question** on a conflict: "this contradicts goal X: update the brief or change the ticket?". If Andy chooses the brief, the build updates `brief.md` in the same PR (docs ship with the change, ADR-0022). `docs/features.md` stays the "what shipped" record, updated on merge; the weekly system review reports drift between the two (later).                                                                        |
| Project `AI`      | Its brief points at ARCHITECTURE §1–3 instead of repeating them, so the control plane dogfoods the mechanism without a second source of truth.                                                                                                                                                                                                                                                                                                                                               |
| Safety            | The brief is untrusted data like every context source (ADR-0033): rendered as plain text in the UI and MCP, size-capped, never instructions to an agent. The API accepts answers only from Andy (signed in, allow-listed).                                                                                                                                                                                                                                                                   |
| When              | M2: Multi-project in parallel, in the onboarding slice (sliced at milestone start). The `context` field on the run request can be added by M1.8: Build + gate if the executor needs it first.                                                                                                                                                                                                                                                                                                |

### Consequences

- Good: every project starts with the same brief, written in a conversation rather than by hand; one procedure serves Claude and the UI; the brief changes through reviewed PRs, so git shows when and why direction changed; agents flag contradictions instead of silently building against stale goals.
- Bad: one more procedure to keep in step with the UI form (the procedure is the source; the form is generated from its question list); the brief can still go stale between tickets if Andy says "change the ticket" every time; another entry point and MCP tool to put in the threat model when built.
