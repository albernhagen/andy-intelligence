# 0043 — GitHub App setup from the UI; repo tokens for CI instead of a review bot App

Decided by Andy, 2026-11-03 (M1.19: GitHub App setup from the UI), after the ADR-0041 runbook turned out too manual: two Apps created by hand, credentials piped through `gcloud`, a second Terraform apply, a CI variable, and a GitHub environment secret.

## Decision Outcome

| Question               | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Creating the App       | From the UI: Settings → GitHub → **Connect GitHub**. The API builds the manifest from its own public URL; the SPA posts it to GitHub; Andy clicks Create; GitHub redirects to `/settings/github/callback?code&state`; the SPA sends the code to `POST /api/github/connect` (signed-in, allow-listed). The API exchanges it once and saves the App. GitHub doesn't let an API create Apps, so that click and the install click stay.                                                                                                                      |
| Forged callbacks       | The SPA makes a random `state`, keeps it in this tab's `sessionStorage`, and only sends the code if GitHub returns the same `state`. A second connect is refused (`409`); there is one App per control plane.                                                                                                                                                                                                                                                                                                                                            |
| Where credentials live | Identifiers (App ID, slug, client ID, owner) in Firestore `config/codeHost`; private key and webhook secret as new versions of the existing Secret Manager secrets (written by the API: runtime SA gets `secretVersionAdder` on those two only). Port `CodeHostConnectionStore` (fake, contract suite, GCP adapter). Secrets are written before the document, so a half-finished save reads as "not connected".                                                                                                                                          |
| Reading credentials    | At runtime, cached 5 minutes per instance (10 s while not connected). Removes the `GITHUB_*` env vars, the `github_app_id` tfvar, the `TF_VAR_GITHUB_APP_ID` CI variable and the second apply; rotation no longer needs a redeploy. Until connected, `/webhooks/github` answers `503` and repos can't be registered.                                                                                                                                                                                                                                     |
| Installing             | The settings page links to GitHub's install page and lists the installed repos (`CodeHost.listInstalledRepos`, live, ≤ 100); the new-project form suggests them.                                                                                                                                                                                                                                                                                                                                                                                         |
| Review bot App         | **Removed.** `POST /github/token` gives a CI job a 1-hour token with contents + pull requests write on its own repo when it presents a GitHub Actions OIDC token (audience = the service URL; issuer, signature, expiry checked against GitHub's JWKS) whose `repository` + `workflow_ref` (includes the branch) match `TOKEN_POLICY`. Today: `system-security-review.yml` on `main` only. ≤ 30 tokens/minute per instance, counted after verification. M1.6: Claude Code executor and M1.8: Build + gate reuse it. No App key or token lives in GitHub. |
| App permissions        | Control-plane App: metadata read, **contents write, pull requests write** (for those tokens), checks read, actions read. No `workflows` or administration permission, so App tokens can't change workflow files or repo settings.                                                                                                                                                                                                                                                                                                                        |
| System review job      | Split: the agent's job has no write credential and no `id-token: write`; a separate `publish` job takes the edited threat model as an artifact, gets the token and opens the PR.                                                                                                                                                                                                                                                                                                                                                                         |

### Consequences

- Good: setup is two clicks on GitHub plus picking repos; no secret passes through a terminal, tfvars, state or GitHub; one App instead of two; rotation without a redeploy; the token endpoint is the base for M1.6.
- Bad: the runtime SA can add secret versions (it already reads them, so a compromised runtime gains nothing new); a leaked App key now gives write access to installed repos (R19); the OIDC check is our code (tests sign tokens with a local key; jose does the cryptography). `TOKEN_POLICY` is in code, so adding a workflow needs a PR. The control-plane URL is written into `system-security-review.yml` (public, not secret).
