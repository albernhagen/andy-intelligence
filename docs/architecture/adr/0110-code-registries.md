# 0110 — Routes, MCP tools and exports register from their own module; `api.gen.ts` is not committed

AI-145: Code registries: adding a tool, route or export doesn't edit a shared file (epic AI-140: Parallel development without merge conflicts).

## Context and Problem Statement

Over 2026-11-06 to 2026-11-20 (117 commits on `main`) the most-touched code files were registries every feature PR appended to: `apps/web/src/lib/api.gen.ts` (31 commits), `apps/api/src/app.ts` (29), `packages/domain/src/index.ts` (28, all appends at the end), `packages/contracts/src/entities/index.ts` (27), `packages/contracts/src/ports/index.ts` (26), `apps/api/src/mcp/tools.ts` (26), `packages/contracts/src/testing/index.ts` (21). Two unrelated PRs conflicted on the same last lines.

## Considered Options

1. Keep the registries; resolve conflicts by hand or regenerate.
2. Discover modules at runtime or build time (folder scan, `import.meta.glob`). The API is bundled by esbuild and typechecked by `tsc`; neither scans folders without a plugin.
3. Each module registers itself; one explicit, sorted list per kind, one line per module, with a test that every module is listed and the list is sorted. Generated files are not committed.

## Decision Outcome

Option 3: the boring one; it needs no new tool.

- **Routes:** a module exports `apiRoutes` (registered after the `/api` sign-in middleware) or `publicRoutes` (before it), both `RouteModule = (app, services) => void`, and gets one `export { … as name } from` line in `apps/api/src/api-routes.ts` or `public-routes.ts`. `app.ts` keeps the middleware, `/health`, `/config.json`, `/api/me` and the OpenAPI document, in the same order.
- **Services:** `apps/api/src/services.ts` builds the shared domain services once; the MCP endpoint takes the same object, so a new service is one field there (and in `ToolDeps` if tools use it).
- **MCP tools:** each `apps/api/src/mcp/tools-*.ts` exports a `ToolGroup` and gets one line in `tool-groups.ts`. The former inline tools moved to `tools-core.ts`. `tools.ts` keeps `ToolDeps`, `run` and the loader.
- **Barrels:** `export … from` lines are sorted by module path (`packages/domain`, `packages/store`, the `packages/contracts` index files), so inserts land in different places.
- **Order:** the lists load in name order. A test proves no two routes can match the same request, so route order between modules has no effect; the `/api` middleware stays between the public and signed-in lists. MCP `tools/list` now returns tools grouped by module name.
- **`api.gen.ts`:** generated by `pnpm --filter @andy/web typecheck` (and `gen:api`), git-ignored. Nothing imports it at runtime (type-only imports), so `vite build` and the Docker image don't need it.
- **Tests** (`apps/api/src/registries.test.ts`): every module that exports routes or a tool group is listed; the lists are sorted; no overlapping routes; no `/api` path before sign-in; tool names unique. `pnpm --filter @andy/api snapshot` prints routes, tool names, the OpenAPI document hash and package exports, to compare two checkouts.

## Consequences

- Good: two PRs adding a route, tool or export conflict only when their sorted lines are neighbours, and then only on that one line. `api.gen.ts` never conflicts.
- Bad: a fresh checkout has no `api.gen.ts` until a typecheck or `gen:api`, so the editor shows errors in `apps/web` until then.
- Not done: the `packages/contracts` index files still hold the schemas, ports, fakes and contract suites themselves; a feature that extends `WorkTracker` or `Project` still edits them. Splitting them per entity is a follow-up, best done when few PRs are open, since git can't follow content moved between files.
