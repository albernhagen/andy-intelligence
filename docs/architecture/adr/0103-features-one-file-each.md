# 0103 — Features: one file per feature, index printed on demand

AI-141: Features list: one file per feature, index generated (epic AI-140: Parallel development without merge conflicts).

## Context and Problem Statement

`docs/features.md` was one hand-edited table. Every feature PR edited it and prettier re-padded the whole table, so each merge conflicted every other open PR. Its single word budget also let two passing PRs push `main` over together. Andy, 2026-11-20: cut merge conflicts to prioritize parallel agent development.

## Considered Options

1. Keep the table.
2. One file per feature, plus a committed, sorted index regenerated by a script and checked in CI.
3. One file per feature, no committed index; a script prints it on demand.

## Decision Outcome

Option 3.

- Each shipped feature is `docs/features/<name>.md`: `# <name>`, a what-it-does paragraph, `**How to use:** …`. Format and folder in `docs/features/README.md`.
- `pnpm features` (`scripts/features.mjs`) prints all features as one table. `pnpm test` checks every file is well formed, names are unique and relative links resolve.
- Context budget: per feature file (`docs/features/*.md`), not one for a table.
- Where ADR-0022, ADR-0053 and ADR-0078 name `docs/features.md`, read `docs/features/**` for this repo. Managed projects keep `docs/features.md` until the template ships the folder.

### Consequences

- Good: two feature PRs touch different files, so they never conflict, and no budget is shared between them.
- Good: option 2 was rejected because a sorted index still conflicts when two PRs insert neighbouring lines.
- Bad: no committed one-page view; GitHub's folder listing or `pnpm features` replaces it.
