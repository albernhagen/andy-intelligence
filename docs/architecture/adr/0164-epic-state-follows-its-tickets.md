# 0164 — An epic's stage follows its tickets

AI-404: An epic's state is computed from its tickets and it closes itself when the last one is Done. An epic is a ticket of type `epic` with a stored stage that nothing moved, so finished epics sat in Backlog and Ready; on 2026-11-26 and 27 a session closed five by hand, four moves each. The roadmap already computed not started, in progress and done from an epic's tickets; MCP `board`, MCP `status` counts, dashboards and the move controls read the stored stage.

## Considered Options

1. **Stored, kept in step.** The stage stays a stored field. After every ticket write that changes a child's stage, parent, archived flag or type, the system recomputes the parent epic and writes its stage as `system` when it differs; the write is the history entry. Every reader keeps reading `stage`.
2. **Computed on read everywhere.** An epic's stage is derived from its children wherever it is read. Readers with the project's ticket list can do it for free, but a single-ticket read (`status AI-x`, the ticket panel, dispatch's epic chain) needs the children, and the per-stage counts are Firestore aggregations that can't see children. "Record it in the epic's history" (criterion 1) needs a write anyway.

## Decision Outcome

Andy, 2026-11-27, on PR #477: "Recommendations are fine." So the per-epic check flag (default off) and a milestone's done following its epics with no click are decided as built.

Option 1. It is one write path instead of a rule in every reader, it gives the history entry for free, and no hot read path (board, ticket list: ADR-0133) reads more.

| Topic         | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Rule          | Over the epic's children (archived too; Cancelled left out): none → **not started** (stored `backlog`); all Done → **done** (`done`); any past Backlog → **in progress** (`in_progress`); else not started. Child epics are children like any other, with their own kept stage, so nesting rolls up level by level. `epicStage` computes it for the sync and the fix-up; readers name the stored stage with `epicStateOf` (not started, in progress, waiting for your check, done).              |
| Needs check   | A per-epic flag `needsCheck`, default off. With it on, "all Done" stores `ready_for_review`, shown as "Waiting for your check", and the owner closes it with the one forward move to Done (web or MCP `move_ticket`). Only the owner turns the flag on or off (owner action `epic_check`), since turning it off closes a waiting epic; agents can do neither. Only an epic can carry it. A Done epic stays Done until a child reopens it.                                                        |
| When          | A tracker wrapper (as `notifyOnNeedsYou` and `bumpOnWrite`) sees every `createTicket` and `updateTicket`. A write that changes `stage`, `parentId`, `archived`, `type` or `needsCheck` syncs the parent epic (and the old parent on a reparent). Any such write to an epic itself puts it back in step at once (a stray stage write, a reopen, a type or flag change). Each moved epic syncs its parent, at most 5 levels up; the sync's own writes go to the inner tracker, so they never loop. |
| Reads         | Per syncing write: the epic (1 read) and its children's counts per stage by aggregation queries (one per stored stage, equality filters only), so the cost is the same for 5 children or 500 (ADR-0028) and a bulk move of N children costs about N × 9 reads, not N × N. None on board, list, roadmap or count reads.                                                                                                                                                                           |
| Write         | Actor `system`, unforced, reason "follows its tickets: N of M done". Leaving Done unarchives the epic. A conflicting write is retried, 3 tries in all. A sync that still fails never fails the child's write: it logs the ERROR `epic stage sync failed` (an alert can match it) and flags the epic Needs-you with a comment, so it reaches Andy's inbox and Needs-you email; the next child write, or the fix-up, heals it.                                                                     |
| Moves         | `move` refuses an epic, forced or not, web and MCP alike: "AI-x is an epic: its state follows its tickets". Exceptions: the owner closing a waiting epic (above), and reopening a Cancelled one (its stage is then recomputed). Refine never moves an epic to Ready. Cancel and archive stay the owner's; a Cancelled epic is never synced. The web panel shows no move controls and no Definition of Ready on an epic.                                                                          |
| Counts        | Epics are left out of MCP `board` lanes and of per-stage counts (MCP `status`, dashboards), as the web board leaves them out (AI-403; one shared `boardCards` rule): an epic is not work, and web and MCP must match (ADR-0148). Their state shows on the roadmap, milestone page, `milestone_map` and `status` with an epic's key, all reading the same stage.                                                                                                                                  |
| Milestones    | A milestone's done stays computed from its epics' stages with no further click (ADR-0131); it now follows its tickets through them.                                                                                                                                                                                                                                                                                                                                                              |
| Existing data | No migration on deploy. An idempotent fix-up script (dry run by default, `--apply` writes) sets every non-Cancelled epic to its computed stage; runbook `epic-state-fixup.md`. Until it runs, each epic heals on its next child write.                                                                                                                                                                                                                                                           |

### Consequences

- Good: one rule, one write path; every reader (board, roadmap, milestone page, `status`, `milestone_map`, digest, dispatch and milestone holds, epic merge mode) reads the same stored stage.
- Good: closing an epic is in its history with who (`system`, or the owner for a checked epic) and why.
- Bad: a write outside the app (console edits) doesn't sync until the next child write or the fix-up.
- Bad: about 9 extra reads on each child write that changes stage or parent (the epic, and its children's counts).
- Who may close an epic doesn't change in substance: before, only moves (owner or a one-step forward move by a session) did; now only the system, or the owner for a checked epic. No security area change.
