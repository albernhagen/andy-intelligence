# Threat model: Promote and rollback

Detail on promote and rollback (AI-199: M6.12, ADR-0160; part of M6: Dev → prod releases in `docs/architecture/milestones.md`, ADR-0114): the owner starts a project's `release.yml`, which changes what serves prod (or dev). The workflow's reports: [deployments.md](deployments.md). Risk register, assets and mitigations: [threat-model.md](threat-model.md). PRs that change this area update this file; the weekly system review edits only the main file.

## Caps (ADR-0028)

| What             | Cap                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| Release requests | One per project per minute, in the create transaction (both instances); `429`                  |
| Workflow runs    | One dispatch per accepted request; GitHub runs one release or deploy at a time per environment |
| Run checks       | One per 45 minutes per open request, none after 6 hours                                        |
| Reads            | At most 100 deployments per environment per request; at most 50 requests per listing           |

## Credentials

None new. The dispatch uses the connected GitHub App's installation token (`actions: write`, which the App has). The control plane holds no cloud credential: the workflow's own deployer identity moves traffic. If an installation lacks `actions: write`, the request is `dispatch_failed` with the reason and nothing changes; the App is never widened from here.

## Residual risks (R-AI-199)

- **Andy's MCP grant can change prod.** Any session holding it (a coordinator) can call `promote` or `rollback`. Mitigations: owner-only, the cap, refusals, and the record of every request with its actor.
- **A cancelled run is shown, not pushed.** The request becomes `cancelled` on the Releases page and in `list_release_requests`; nothing lands in Needs-you yet.
- **A refused rollback start still runs.** `release.yml` doesn't stop a rollback when its start report is refused, so a mismatched or replayed request still moves traffic, unrecorded. Only someone who can start workflows in the repo can send one.
