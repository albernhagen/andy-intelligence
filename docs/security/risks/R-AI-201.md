# R-AI-201

**Risk:** AI-201: M6.16: Project environment module gives each managed project a main deployer, `<service>-deploy`, that GitHub Actions can use without a key. Whoever can run `deploy.yml` or `release.yml` on that repo's `main` can push any image to the main registry repo and roll it out on the main service with the main runtime identity's data access. That is anyone who can merge to `main` (Andy, the coordinator, the gate's auto-merge) or start `release.yml` (repo write access, and the control plane's GitHub App through promote). A workflow on `main` with a dangerous trigger (`issue_comment`, `pull_request_target`) in one of those two files would hand the identity to outside input.

**Mitigation / next step:** Federation is bound per file on `workflow_ref` = `<repo>/.github/workflows/{deploy,release}.yml@refs/heads/main`: PRs (`refs/pull/N/merge`), other branches, tags and every other workflow on `main` are refused, and the provider accepts only the one repo by name and numeric ID (a re-created repo of the same name gets a new ID). Grants are on one service, one registry repo and one runtime identity, in that project only; no IAM, no project roles. A PR that changes `.github/` is a kept kind: only Andy merges it (ADR-0124), so a new trigger in either file needs his review. ADR-0114 fixes their triggers (push, `workflow_dispatch`) with no secrets in inputs.
