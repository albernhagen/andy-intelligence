# R-AI-206

**Risk:** Managed-repo deploy identities' use (AI-206: M6.17). A `cloud-run` project's baseline `deploy.yml` and `release.yml` hold its `<service>-deploy` identity: anyone with write access to that repo's `main`, or who can dispatch `release.yml`, can deploy any code to the first environment and promote a digest or roll back prod. The workflows trust repo variables for which project, service and identity to use, and run andy-intelligence actions at the baseline's SHA.

**Mitigation / next step:** The identity federates only from those two files on `refs/heads/main` of one repo (name and numeric ID pinned) and can only push to its own registry repo and deploy its own service (`project-env`). `id-token: write` only in the job, only on `main`; no `pull_request` or `repository_dispatch` trigger (a test checks). Variables and dispatch inputs are checked before any build or cloud call; values reach scripts through `env`; multi-line values are refused. Actions pinned by full SHA. Promote is gated by the control plane's `422` (no succeeded dev deployment of that digest). Promote in `dev-and-prod` fails before traffic moves until AI-390: Promote in dev-and-prod: prod deployer reads the dev registry. Next: the owner-only promote and rollback routes (AI-199: M6.12: Promote and rollback from UI and MCP) and branch protection on managed `main`. Detail: `deploy-caller.md`.
