# R-AI-386

**Risk:** A build's approved plan now names npm packages that a trusted executor job resolves into the manifests and lockfile before the agent starts (AI-386, ADR-0156). Plan text is agent output from ticket text, so a hostile ticket could steer a plan to a typosquatted or freshly hijacked package, or try to make the install step fetch from somewhere other than the registry, run code, or change other files. A compromised package would then reach the agent's checkout and the PR.

**Mitigation / next step:** Andy approves every plan that names packages (the plan-approval gate; a build that needs an unnamed package stops and forces a new plan, whatever the policy). Names are checked against the npm name grammar three times (plan schema, the executor's context check, `executor-deps.mjs`): no version, URL, `git:`, `file:` or alias, workspace repo-relative without `..`, at most 5. The `deps` job holds no model credential, OIDC token or write token; pnpm runs `add --lockfile-only` with install scripts and pnpmfile hooks off and a 7-day release-age cooldown (a fresh hijack is usually caught inside that window), and any change but the named `package.json` files and `pnpm-lock.yaml` is refused. The job refuses a pnpm older than 10.16 (which would silently ignore the cooldown) and a project setting that exempts packages from it, and both jobs refuse a lockfile with a git, tarball or directory source (the CI lockfile-source rule), so a plan package can't pull an exotic transitive dependency into the frozen install. The agent job applies the files only if they were resolved on its own commit and are exactly those files; the sandbox keeps them read-only. The PR carries the change, where dependency review and the lockfile-source check (registry with integrity only) run, and the gate counts it as tooling files, so it never auto-merges. Residual: a malicious package older than 7 days that Andy approves; dependency review and his merge are the last checks.
