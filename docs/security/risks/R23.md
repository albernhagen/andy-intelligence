# R23

**Risk:** A coordinator session merges PRs to `main` without Andy reading them, while reading untrusted ticket text, PR text, review comments and worker reports; injected text or a weakened reviewer could pass a harmful PR. Sessions still hold Andy's GitHub token, so one could merge directly.

**Mitigation / next step:** Sessions merge only through MCP `merge_pr` (AI-220, ADR-0124): owner only, 30 calls per project per hour, GitHub facts only, `mergeVerdict` under the merge mode, App token, squash, pinned to the judged head. Clean is code: every check and both reviews passed on the head, head contains the latest `main` (base tip re-read before merging), no open finding or accepted label, the PR's linked ticket in Ready for review, no kept path. Docs-only and agent PRs never merge through it. Every merge into a default branch, `merge_pr`'s and the gate's, goes through the repo's merge queue (AI-110, ADR-0150): one at a time per repo across instances (a leased store record), the next PR synced and re-judged on the new `main` first; the lease is renewed just before each merge call; only one call can outlive its 90 s lease. Kept paths: only code refuses them (`mergeVerdict` checks `KEPT_PATHS` in `merge_pr` and the gate). GitHub does not (AI-380): the only code owner authors every PR, and code-owner review at 0 approvals let PR #409 merge a kept path unreviewed; 1 required approval would block every App merge (runbook `onboard-a-repo.md` §1b). Procedural: not merging with Andy's token, which passes code and GitHub alike (`coordinate.md` §7, runbook §5); "open finding or doubt". `protect-main` requires every check and both reviews; review procedures come from the base branch (R5); each merge gets a release note (AI-159) and a ticket comment.
