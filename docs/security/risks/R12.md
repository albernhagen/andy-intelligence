# R12

**Risk:** A stolen MCP refresh token works until its own 30-day limit (Anthropic holds it; local sessions keep it in the keychain). Rotation happens only in a token's last 7 days and never shortens the old one (ADR-0158: Rotate MCP refresh tokens only near expiry), so using a token is no longer a theft signal: the trade for many sessions sharing one sign-in without dropping. Access tokens last 1 h.

**Mitigation / next step:** Fixed 30-day limit (use never extends it); allow-list re-check each refresh; every refused refresh logged with reason and token age; revoke by deleting `oauthGrants` (runbook `mcp-connector.md` §5). A thief can create backlog tickets, answer questions (Andy still merges), step tickets forward, and edit, comment on, re-parent and reorder them (AI-40: changing what an agent builds or what runs next; history records each change); no delete, forced move or release. No token-family revocation, by choice: ADR-0158 rejected it, because a stale session reusing an older token is normal and a reuse rule would sign every session out (AI-211: MCP OAuth: revoke a stolen token's chains together, Andy, 2026-11-27). Revoking means deleting the whole collection, which also removes every chain minted in a token's last 7 days. A refresh in flight during the delete can write new tokens after it; the runbook's revoke step re-checks the collection a few seconds later.

**Revisit** when `start`, `set_override` or `promote_release` land: a family ID on every grant from one sign-in, plus a revoke tool that marks a family revoked so tokens minted in flight are refused too.
