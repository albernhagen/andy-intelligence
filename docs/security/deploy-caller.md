# Threat model: Deploy caller in managed repos

AI-206: M6.17. A `cloud-run` project's `deploy.yml` and `release.yml` (from `template/.github/workflows/`, written by the baseline) use the main deployer identity `project-env` creates in that project's GCP projects. Identities and their bindings: `infrastructure.md` (R-AI-201 to R-AI-201-4); the deployment callback: `deployments.md`.

## Trust boundaries and entry points

| Entry point                         | Who can reach it                                       | Authn/authz                                                                                                                                                                                                   | Notes                                                                                                                                                                                                                     |
| ----------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deploy.yml` (push to `main`)       | Whoever can push or merge to the managed repo's `main` | Job runs only on `refs/heads/main`; `id-token: write` in that job only; the deployer federates only from `deploy.yml`/`release.yml` `@refs/heads/main` of that repo (repo name and ID pinned in the provider) | Builds and deploys the repo's own `main`. Bot merges (`dependabot[bot]`, `github-actions[bot]`) skip, as in the control plane                                                                                             |
| `release.yml` (`workflow_dispatch`) | Repo write access; the control plane's App token       | Same; a dispatch off `main` gets no job and no token                                                                                                                                                          | Inputs are untrusted: they reach the scripts through `env` only and are checked first (`scripts/cloud-run-caller.mjs`, `cloud-run-release.mjs`)                                                                           |
| Repo variables (`toJSON(vars)`)     | Repo admins                                            | GitHub repo settings                                                                                                                                                                                          | Names, not credentials. Each value must be one line (a newline could forge another step output, so it fails). A wrong variable can only point at something the deployer can reach: its own project's service and registry |
| Pinned actions (`…@<sha>`)          | andy-intelligence `main` at the baseline's SHA         | Full commit SHA, written by the baseline; third-party actions inside them SHA-pinned too                                                                                                                      | Satisfies the managed repo's `sha_pinning_required`. A new action version reaches a repo only when the baseline is re-run there                                                                                           |

## Credentials

No new credential. GitHub OIDC → the environment's Workload Identity provider → `<service>-deploy` (push to `<service>` registry repo, `run.developer` on `<service>`, actAs `<service>-run`; on prod in `dev-and-prod`, also write on the dev `<service>` repo so promote can check the digest, AI-390: Promote in dev-and-prod: prod deployer reads the dev registry, and tag it `release-<hex>`, AI-389: M6.23: Deploys and promotes tag the image prod runs, R-AI-389). The same job token, audience the control plane, signs the deployment reports.

## Residual risks (R-AI-206)

- **Repo write access deploys.** Anyone who can merge to `main` or dispatch `release.yml` can ship code to that project's first environment and promote or roll back prod, within that project only. Risk file: `risks/R-AI-206.md`.
- **The baseline keeps files once written.** Changing `deployKind` from `cloud-run` to `none` leaves both workflows in the repo; delete them by hand.
