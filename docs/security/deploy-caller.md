# Threat model: Deploy caller in managed repos

AI-206: M6.17 and AI-207: M6.18. A `cloud-run` project's `deploy.yml`, `release.yml` and `preview.yml` (from `template/.github/workflows/`, written by the baseline) use the main deployer identity `project-env` creates in that project's GCP projects. Identities and their bindings: `infrastructure.md` (R-AI-201 to R-AI-201-4); the deployment callback: `deployments.md`.

The template Terraform root the baseline seeds in a `cloud-run` repo's `infra/` (AI-109: M6.22) adds no entry point or credential: it only calls `project-env` and `project-budget`, applied by Andy with his own login. Its real values (project IDs, billing account, alert email) live in the gitignored `infra/terraform.tfvars`; its state, which holds them too, in a versioned `gs://<prod project>-tfstate` bucket in the prod project: no public access, readable by that project's members, last 10 old versions kept (R-AI-109). The repo copy has fake example values only (a test checks).

## Credentials

No new credential. GitHub OIDC → the environment's Workload Identity provider → `<service>-deploy` (push to `<service>` registry repo, `run.developer` on `<service>`, actAs `<service>-run`; on prod in `dev-and-prod`, also write on the dev `<service>` repo so promote can check the digest, AI-390: Promote in dev-and-prod: prod deployer reads the dev registry, and tag it `release-<hex>`, AI-389: M6.23: Deploys and promotes tag the image prod runs, R-AI-389). The same job token, audience the control plane, signs the deployment reports. `preview.yml`: OIDC → `<service>-pr-deploy` (push to the `<service>-preview` registry repo, `run.developer` on `<service>-preview`, actAs `<service>-pr-run`, which has logs and traces only), plus the job's `GITHUB_TOKEN` with `pull-requests: write` for the one comment.

## Residual risks (R-AI-206, R-AI-207)

- **Repo write access deploys.** Anyone who can merge to `main` or dispatch `release.yml` can ship code to that project's first environment and promote or roll back prod, within that project only. Risk file: `risks/R-AI-206.md`.
- **PR code runs with the preview deployer (R-AI-207).** A PR from a branch of the repo can, through its own `preview.yml` or Dockerfile: push any image to the preview registry; deploy any revision to `<service>-preview` (as `<service>-pr-run` only, so no prod data); move or remove other PRs' `pr-<n>` tags or route the preview service's traffic; raise the preview's per-revision scaling (drift on the next plan; the project budget and alerts catch spend); read the job's `GITHUB_TOKEN` (`pull-requests: write`, `contents: read`). It can't touch the main service, its registry or runtime identity, make the preview public (no `setIamPolicy`), or reach another project. Risk file: `risks/R-AI-207.md`.
- **The baseline keeps files once written.** Changing `deployKind` from `cloud-run` to `none` leaves both workflows in the repo; delete them by hand.
