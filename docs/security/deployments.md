# Threat model: Deployment reports

Detail on the deployment record's entry point (AI-180: M6.4, widened by AI-190: M6.11 for releases; part of M6: Dev → prod releases in `docs/architecture/milestones.md`, ADR-0114). Each deploy, promote and rollback reports `started` and then `succeeded` or `failed` (environment, commit, image digest, revision), so release notes, verification and the DORA metrics (ADR-0040) read one record the control plane keeps. The report is authenticated like the run callbacks (ADR-0019) and never fails the deploy. Risk register, assets and mitigations: [threat-model.md](threat-model.md). PRs that change this area update this file; the weekly system review edits only the main file.

## Trust boundaries and entry points

| Entry point                                                                          | Who can reach it                                                   | Authn/authz                                                                                                                                                                                                                                                                                                                                                            | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /deployments`, `POST /deployments/{id}/finish` (`apps/api/src/deployments.ts`) | Internet; meant for a project's own `deploy.yml` and `release.yml` | GitHub Actions OIDC token (ADR-0019): issuer, audience (`PUBLIC_URL`), signature and expiry checked. `workflow_ref` must be exactly `<repository>/.github/workflows/deploy.yml@refs/heads/main` or `…/release.yml@refs/heads/main`, and the repository must belong to an enabled registered project. Anything else is `403` with nothing written; a bad token is `401` | The token, not the body, sets the project and the workflow. Start body (`DeploymentStartReport`): image digest, and optionally `environment` (`dev`, `prod`; default `prod`), `kind`, `url` (https, no credentials) and `request`; unknown fields refused (`400`). Rules (`packages/domain/src/deployment-reports.ts`): `deploy.yml` reports only kind `deploy`, with the token's commit; `release.yml` only `promote` (to prod, from a succeeded dev deployment) or `rollback` (from a succeeded deployment in the same environment), with that deployment's commit: no such deployment of the digest, or a wrong kind, is `422` with nothing written. A finish: a deploy only by the same project's `deploy.yml` at the same commit, a release only by the same project's `release.yml` (`404` otherwise), and only once (`409`). |

## Caps (ADR-0028)

| What             | Cap                                                                                                                                                  |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Body             | 1 KB, refused before parsing (`413`)                                                                                                                 |
| Verified reports | 30 a minute per instance, after verification, so forged tokens can't use it up (`429`)                                                               |
| Writes           | One document per start, one update per finish; reads: the deployment, the latest good one and, for a release, one listing of at most 100 deployments |

## Credentials

No new credential. The deploy and release jobs hold `id-token: write` (for Workload Identity Federation); the same job token, with the control plane as audience, signs the reports. The report step masks it and never logs it (`platform/actions/report-deployment`).

## The release workflow (`release.yml`)

| Check                | How                                                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Who starts it        | `workflow_dispatch` only; the job runs only on `refs/heads/main` (the deployer identity is bound to it). Anyone with repo write access can dispatch it; M6.12 adds the owner-only API route |
| Inputs               | Public in run logs, no secrets. Reach scripts through `env`, never interpolated into a `run:` line (a test checks); checked first by `scripts/cloud-run-release.mjs inputs`                 |
| Before traffic moves | Promote: the digest is in the registry. Rollback: the revision belongs to the service and is ready. Otherwise the job fails with nothing recorded and no traffic change                     |
| Overlap              | Concurrency group `deploy-<environment>`, shared with `deploy.yml` for prod; never cancels a running release                                                                                |
| Permissions          | `contents: read`, `id-token: write`; no new IAM: `roles/run.developer` and `roles/artifactregistry.writer` already cover the reads and the traffic change                                   |

## Residual risks (R-AI-180, R-AI-190)

- **Push access to `main` can write records.** Whoever can change `deploy.yml` on `main` (Andy; later collaborators) can report deployments with any digest and status. The record is informational until verification and promotion read it (M6.5 on); those tickets recheck what they act on.
- **Rerun of an old workflow run.** A rerun of an earlier `deploy.yml` run on `main` reports a new deployment of that earlier commit, which is true: it did deploy it again.
- **Lost reports.** A report that fails (control plane down, deploy of the control plane itself in progress) is a job-summary warning; the deploy goes on and the record is missing or stays `started`. The first deploy containing this route reports to the old revision, which answers `404`, so that one deploy isn't recorded.
- **Repo write access can roll back or promote.** Anyone who can dispatch `release.yml` can move prod traffic to any ready revision or ship any digest in the registry, as they can already by pushing `deploy.yml`. Risk file: `risks/R-AI-190.md`.
- **A release run may finish another release's record** of the same project (no commit to match). One release runs per environment, so this needs a stuck record from an earlier lost finish.
- **Rolling the control plane back past AI-190: M6.11** lands on a revision whose callback refuses `release.yml`, so that rollback's finish report is lost and its record stays `started`.
